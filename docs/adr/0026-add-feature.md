# 0026: Add a feature

Date: 2026-10-29 · Status: accepted · Phase 11

## Context

CODEWRIGHT.md 5.13: `add_feature`, tier 2. Product Manager stories, Solution Architect design (approved), builds by
the developers, tests from acceptance criteria, verify (tests, replay, preview), review, approve, deliver. The model
is a 9B one with a 4K context: it cannot lay out a layered feature from scratch reliably (live runs proposed invented
paths and the wrong layers), and it rewrites one file of at most ~3,600 characters at a time.

## Decision

- **Feature by analogy** (`feature/analogy.py`). Most features look like one the app already has. Existing features
  are found by file stem across at least 3 folders (`wishlist` in model/, repository/, service/, port/http/...). The
  model only picks the analog and names the new feature (normalized; the search's closest feature as a fallback).
  The plan then follows the analog's real files: each becomes a new file adapted from it, files that wire the analog
  in are changed next to it, long files that declare the analog's types get the new declarations appended, and a
  numbered migration is added when the analog's table comes from migrations. Generated files (mocks), files too long
  to adapt, tests that need those mocks, and long UI files to wire by hand are left out and listed in the plan.
- **Free design fallback** when nothing is similar: the model lays out up to 8 files; whether each is new or changed
  is read from the workspace, unsafe paths are dropped, and the drops are listed.
- **Build in dependency order**: appended types, then model and migration, repository, service, handlers, tests,
  then wiring. Each file sees the declarations (with struct/class fields) of the files written before it, nearest
  layer first. Feature files use their own rewrite rules (new behavior; a signature in the new code may change);
  refactor rules forbid exactly that. Then build and test, up to 5 fix rounds, each fixing the files the errors name
  (paths resolved from the component a tool ran in).
- **All or nothing**: a feature that never gets green is removed completely (originals restored, new files deleted).
  It is committed only when the tests pass and a new migration applies and rolls back on a fresh PostgreSQL
  database (the Phase 10 trial). Replay must show existing behavior unchanged; a screenshot is taken when web files
  changed.
- **Cancel leaves the project as found** (all playbooks): a cancelled run on a `codewright/` branch has its unfinished
  changes stashed (`git stash list`), the project goes back to its previous branch, and the run's branch is deleted
  if nothing was committed on it.
- Kept generic: entry files are detected by name in any language; prompts carry no project-specific examples.

## Consequences

Quality depends on having a similar feature and on the model; the gates and the all-or-nothing rule make a bad
result visible and harmless. Acceptance-criteria tests are only as broad as the analog's adaptable tests (mocks are
generated by tools Codewright does not run yet).
